# 版本命名约定

## 日常开发与公开发布（2026-11-07 明确）

营销版本与构建号分开管理：营销版本描述对外发行阶段，build 标识实际构建。日常修复可以连续生成多个 build，不因一次修改、测试或本机更新创建新的 RC；在所有者决定公开某个阶段成果时，才确定营销版本并发布。build 在营销版本变化后继续递增，不归零，也不人为跳到很大的数字。很多软件的五位 build 是长期开发或 CI 分配的结果，不表示应复制其数字规模。

当前已有 `IdentityVReleaseVersion`（完整发行名）、`CFBundleShortVersionString`（Apple 基础版本）和 `CFBundleVersion`（build）三个字段，技术上早已解耦。最近 RC5 的多个本机构建只是同一营销版本下的开发迭代；过去以 RC 命名隔离目录、在状态页逐次追加构建流水及陈旧的“当前源码版本”描述，容易误导维护者，应使用下面的职责而不按旧目录名推断发布。

- 日常开发：只递增 build；源码提交记录功能变化，当前状态只保留最新交付与未完成项。尚未决定下一次营销版本时不预先宣布 RC 或发布。
- 构建：在准备生成下一份要保留、安装或交接的不同 App 前，先把 `playerLauncherApp/Info.plist` 的 build 递增并形成源码检查点，再构建；同一提交重试失败构建不必再次改号。并行任务不独立分配正式 build，由整合者分配，避免不同字节使用同一 build。
- 发布：确定营销版本、审定 CHANGELOG 和最终源码，再完成匹配的构建、签名、公证、发行物校验与发布。不能覆盖已公开的同号资产；开发构建沿用营销字段不等于再次发布该版本。
- 目录：常用入口只保留 `Projects/IdentityV-Launcher`；临时 worktree 只在独立并行确有必要时创建，整合并保存提交/用户修改后退役。构建、发布及上传产物放 `Builds/IdentityV-Launcher/`，不得留在 Projects 顶层。

这些做法用于区分“写了一次代码”“产出一份 App”和“向用户发布一个版本”，减少版本与临时副本膨胀；不新增开发与发布之间的强制产品阶段。

## 原有版本选择与兼容约定

2026-09-09，风吟为第一版选择 **1.0.0-rc.1** 作为首个发布候选的版本名。该候选已于 2026-09-23 公开发布（Git tag `v1.0.0-rc.1`，提交 `3bac291`）。此前“Alpha 1 / Alpha1-RC1”为开发候选名称，后续不再用于新包。已发布物、后续开发和本机安装物必须分开识别；实际行为与待修复问题见[变更记录](../CHANGELOG.md)和[已知问题](../docs/knownIssues.md)。

2026-09-10 补充封版节奏：RC1 已打通基本可用性，目前尚无首位外部用户，RC2 不急于封版。日常修复持续提交、验证和积累，不按一个补丁对应一个 RC，也不因为本机装了新修复就自动改发行号或封包。由风吟判断何时有阶段性进步，再确定下一次 RC 的范围与封包；emoji 修复当前记为 RC1 之后的未封版改进，不预先锁定为 RC2。

采用[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)的格式和预发布顺序，并将应用的用户可见行为、安装/配置格式与集成接口作为兼容性判断依据：

| 版本 | 项目含义 |
| --- | --- |
| `1.0.0-rc.1` | 2026-09-23 已公开的首个发布候选；字节与 Git tag 固定 |
| `1.0.0-rc.2` | 2026-10-05 已公开，内部构建号6；字节与 Git tag 固定 |
| `1.0.0-rc.3` | 2026-10-09 联系身份同步修订，内部构建号7；构建、公证与发布分别核验 |
| `1.0.0` | 第一版正式发布 |
| `1.0.1` | 向后兼容的问题修复 |
| `1.1.0` | 向后兼容的新功能 |
| `2.0.0` | 重大不兼容变化 |

`0.x`表示早期、尚未承诺稳定的阶段，本身不等于测试版；`rc`表示目标版本的发布候选。两者可以同时使用，但不符合本项目目前准备发布第一版的意图。若未来用alpha/beta，则顺序为alpha→beta→rc→正式；不需要为了形式补发未经历的阶段。

公开发布后，同一版本号对应固定发行物；后续修改可以先留在开发提交中积累，再次公开封包时使用新版本号。内部构建可递增构建号，但不能以只改构建号的方式覆盖已公开发布的同名发行物。正式签名/公证也应在候选公开发布前完成；公开的新候选相对旧候选有二进制变化时，递增 rc。此处约束发行物不可覆盖，不要求每次修改立即发行。

`playerLauncherApp/Info.plist`是版本数据源：`CFBundleShortVersionString`保留macOS要求的纯数字基础版本，`IdentityVReleaseVersion`记录完整版本，`CFBundleVersion`为内部构建号。关于窗口、版本与更新提示和DMG/材料包名读取这份数据。实际第三方组件（例如 idv-login 6.3.0、Wine）的独立版本不随启动器一起改号；发行材料中的组件版本和源码引用仍须与这份 App 实际携带的下载清单/补丁版本相符。

本机开发和测试构建沿用当前发行版本，只递增 `CFBundleVersion`；源码提交、运行时身份/版本及包内清单哈希由 `build-provenance.json` 区分。测试是对构建所做的验证及其结果，不是版本字段；测试可以针对任一构建进行，也可以覆盖多个提交或多个构建。构建号标识实际生成的 App 构建，不要求每个 Git 提交都生成一个构建。这样仓库可以持续接收修复，而本机装入新构建不会被误认成新的 RC。只有决定形成下一次公开候选时才改 `IdentityVReleaseVersion`（例如 `1.0.0-rc.2`），并按前述规则从确定的提交封包。`1.0.0-rc.1-test.1` 与 `1.0.0-rc.1-test.2` 是 2026-09-25 之前已产生的本机测试标识，保留作历史记录；后续不再用 `-test.N` 给每轮本机构建递增发行版本。

候选定稿、正式签名公证和公开发布是分别记录的动作。RC1 已公开，后续源码或运行时变化不得再沿用这个发行号。构建脚本把源码提交、发行号、运行时版本与默认 engine、包内清单哈希写进 `build-provenance.json`；封包前核对它们，并拒绝已存在 Git tag 的发行号。这能挡住“编译的是另一套运行时”及同号重封，但不能替代游戏内功能实测。若只是日常开发构建，仍可沿用当前版本号，直到决定下一次封包范围。
